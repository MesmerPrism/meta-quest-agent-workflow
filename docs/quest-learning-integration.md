# Integrating Quest experiments into reusable tools

Promote the useful operation and its contract, not an entire private diagnostic
application. Reuse current owner seams before adding a second registry or
another generic runner. Device evidence, a source candidate, canonical merge,
consumer adoption and distribution eligibility remain separate milestones.

## Owner and consumer map

| Reusable part | Owner and integration surface |
| --- | --- |
| Device procedure and learned selection criteria | This repository's focused playbooks and short meta-quest-workflow router |
| Android/OpenXR/Spatial SDK effect, packaging, buffers and effective receipts | Rusty Quest library/AAR/native or Java/Kotlin component, composed into a selected APK |
| Windows install/launch/capture/operator and evidence UI | Rusty Hostess CLI/API/WPF adapter consuming the platform owner's receipts |
| Accepted commands, sessions, renewals and stream control | Rusty Manifold contracts and actual app/session owner; not another browser broker |
| Pose/space relations, renderer-neutral visual or compute contracts | Rusty Lattice, Optics or Matter respectively, with platform adapters remaining in Quest |
| Utility demonstration and explicit developer capability | Rusty Kiosk feature/module with its declared caller/permission and escape behavior |
| Ordinary/store-distribution candidate | The selected Launcher Lite product owner, after its actual source and platform/distribution eligibility are reviewed |
| Product workflow, presets, private recording rules and secrets | The owning application/private planning surface |

Hostess's companion catalog/session/report projections already provide the
host-side descriptor and evidence pattern. Extend the applicable existing
module/action path rather than making UI state a registry. Its project-runner
planning support must not be described as universal live execution: the
inspected implementation rejects execute mode. Hostess's current scope also
excludes long-lived background services. An unattended media/session keeper
belongs to the participating app/service owner, with a Hostess control/report
adapter where appropriate.

Rusty Quest's existing
[media session](https://github.com/MesmerPrism/rusty-quest/blob/main/docs/MEDIA_SESSION_RUNTIME.md)
and [media stream](https://github.com/MesmerPrism/rusty-quest/blob/main/docs/MEDIA_STREAM_RUNTIME.md)
composition separate source, processor, route, socket, codec, sink and cleanup.
Use those seams for a new capture source or shader processor. Do not duplicate
all seven in a sample APK or move app-specific session policy into Hostess.
Keep high-rate video, poses and GPU data out of generic control/status.

## Useful extraction slices

### Shared shell recenter operation

Rusty Quest's [shell recenter module](https://github.com/MesmerPrism/rusty-quest/blob/de777c105e400828011d0f8d97256dd6cf15fc2b/docs/SHELL_RECENTER.md)
and [local host provider](https://github.com/MesmerPrism/rusty-quest/blob/de777c105e400828011d0f8d97256dd6cf15fc2b/docs/SHELL_RECENTER_HOST.md)
own the fixed VrShell recenter AppFunction implementation. Hostess exposes its
typed companion action through the existing catalog, CLI, report and operator
UI contracts. Kiosk's `examples/quest-shell-recenter` developer utility consumes
the same source-pinned provider. The utility is an explicit operator path; it
does not add shell permissions or behavior to ordinary Kiosk or Launcher Lite.

The operator supplies the exact current target/route/boot, firmware source
hashes, helper artifact, clean Quest revision/tree/source ID and operator
identity in a private profile. Coordinate custody and calibrated-scene effects
before running a live readiness check or recenter. Readiness performs no
recenter; use another fresh request for the deliberate operation. Passive
status/reconcile observes the saved original and never contacts a headset.

The helper syncs the original intent before its single dispatch. An expired
observer or returned cancellation never permits retry, deletion or process
killing. Keep the original through its real callback, durable final, complete
stream EOF, reap and exact owned-stage cleanup. In-process callers likewise
create a fresh backend, operation and journal for each original. Preserve an
original error and code, held/unknown cleanup and late callback separately from
any independently observed pose or wearer-visible effect. Host and neutral
consumer conformance do not establish an on-headset recenter result.

1. **Developer shader loop:** reuse the existing graphics preparer, current
   optimized ABI/variant comparison, guarded batch transfer and exact revert.
   A Hostess adapter can expose that owner operation and timing/evidence;
   the SDK integration stays in the APK. See
   [feedback loops](quest-development-feedback-loops.md).
2. **Input automation:** package the selected Meta layer and optional capture
   closure in the APK; expose repeatable original actions and input/callback
   evidence through the host adapter. See
   [Operator automation](meta-xr-operator-input-automation.md).
3. **Visibility and system actions:** preserve the ordinary APK visibility
   signal, the separately privileged shell companion and their distinct
   failure/escape behavior. A Kiosk demo is a consumer, not the generic policy
   owner. See [shell investigation](quest-shell-capability-investigation.md).
4. **Capture/effect processing:** extract a selected source or processor only
   after real frame ownership, release and output evidence; retain unsupported
   paths and wearer limitations. See
   [compositor lessons](quest-compositor-experiment-lessons.md).
5. **Lifecycle/performance evidence:** provide reusable counters, process-birth
   and lifecycle attribution, exact-symbol allocation analysis, and compatible
   baseline/candidate comparisons. Keep product meaning and acceptance in its
   owner. See [memory profiling](quest-memory-profiling.md).

For an extraction, record its inputs, action/acknowledgement, effective status,
unknown/reconciliation behavior, output lifetime and cleanup. Give UI and
typed CLI/API callers the same original handler. Demonstrate the reusable
property through a neutral harness or an independent consumer before calling
it a general module; keep the private proof separate from a sanitized fixture.
This is a proportional engineering decision, not a prerequisite for unrelated
product iteration.

## Kiosk and distribution

A shell-launched utility and an ordinary app can present similar UI while
holding different permissions. Prefer the ordinary supported route when it
meets the goal. Put explicit developer-only capabilities behind a clearly
selected Kiosk/tool feature. Review any Launcher Lite candidate against its
actual product manifest, SDK/API use, protected decisions, background behavior,
entitlement and current official distribution requirements; a shell success is
not an eligibility decision.

Do not confuse Launcher Lite with Rusty Kiosk's separate fixed trusted-package
front-door launcher. That front door's deliberately small manifest is its own
contract, not a constraint or capability inventory for another product.
The historical experiment audit did not establish a Launcher Lite source pin
or a new Store approval.

## Adoption order

Keep the evidence and unknowns first, select the owning reusable boundary,
make the smallest source/documentation change, then validate an actual consumer.
Preserve unchanged qualification while checking the real composed caller and
production serialization. A passing isolated helper did not catch several
filename, mode, REPL, hardlink and package-contract failures in actual callers.
Use one current checkpoint and meaningful milestones so compaction or a side
question cannot resurrect an obsolete task. Estimates guide investigation;
actual expiry, current ownership and unresolved effects still govern actions.
